## 服务入口与分流

Mixer 为主 Retrieval Proxy 和 GprHub 侧路创建并发任务。GprHub 侧路命中后，再读取位置级生成式开关：

- 开关开启：调用 GprHub 的生成式召回 RPC；
- 开关关闭：在侧路内部调用旧 GPR 对照 RPC；
- 侧路未命中或调用失败：主 Retrieval Proxy 仍继续执行。

正式与灰度环境不会因为 GprHub 命中而停掉主路；跳过主召回只用于满足专用条件的隔离仿真。GprHub service 按 position 拆分请求并异步执行。`BuildSinglePosRequest` 必须重写对应 position 的 `pos_id` 与 `exp_param`，否则多广告位会串参数。

## `GenerativeData` 共享上下文

新 DAG 的六个 Op 通过 `GenerativeData` 传递状态，避免每个节点重复解析请求。核心字段可分为：

- 请求：position、实验参数、策略和 quota；
- 用户：模型输入上下文、行为序列；
- 模型：encoder embedding、model version、data name；
- 搜索：beam、tree level、unique filter、SID 与 score；
- 库存：TID、AID、creative list；
- 监控：exp tag、recall path、分段状态。

这是一条强类型流水线。修改字段时必须检查生产者、消费者、缓存序列化和监控四个位置。

## 六个生成式 Op

### 1. Entry

从 position 实验参数和 quota plan 得到：

- tree/trie/KV 版本；
- `pam_beam_width`；
- `beam_search_topk`；
- beam 分片比例；
- recall strategy 与 output quota；
- multi-level / anyrecall 模式。

新链路的 `pam_beam_width` 缺省回退到 180，并要求不超过模型/Decoder 支持的最大宽度 180。共享结构中虽然存在 200 的初始值，Entry 会在运行时用位置参数或 180 的安全值覆盖它。

### 2. Datahub

`QueryGenerativeToken` 获取生成式行为序列与上下文。它不是重复拉取 Mixer 的全部用户特征，而是为生成模型准备专用序列。监控需区分空序列、业务过滤后为空和 RPC 失败。

### 3. Encoder

组装多阶段模型请求，执行第一阶段编码，返回：

- 用户共享 embedding；
- model version；
- 后续 Decoder 所需的模型上下文。

Encoder 是一次请求内可复用的部分；多路搜索如果重复编码会浪费主要算力。

### 4. Decoder

逐层 beam search，输出 SID 和累计分数。请求携带：

- shared user embedding；
- `data_name` / model version；
- 多级树参数；
- beam width/top-k；
- unique filter。

结果中的每级 token按协议打包成 `sid_key`。详细搜索语义见 [[推荐系统理论/OneRec/Beam-Search\|Beam Search]]。

### 5. KV Creative

按 SID 查询多个 KV 分片，得到 TID 列表。各分片返回结果用 Z-order/interleave 方式交织，避免单分片排序靠前的结果占满 quota，然后执行截断。

若显式 quota 缺失，代码中存在 1000 的兜底上限。这个兜底应仅用于防止无界返回，不能替代策略层 quota。

### 6. Creative List Build

将 TID 映射为 AID 和创意对象，按 AID 去重并保留生成分数与子策略，输出公共 `MultiAdCreativeList`。从此处开始，生成式候选可以进入原有广告召回公共链路。

## 公共下游

```text
AdListMerge
  → OutputQuotaControl (+ diversity)
  → RecallExit
  → CreativePropertyFilter
  → CreativeServer
  → Sharding
  → Scoring
  → ScoringExit
  → RetrievalCache
```

生成式实现与 GprHub 内部旧 GPR 对照在公共下游大体同构，这是做 A/B 归因的基础。当前两张静态 DAG 仍有少量节点差异，评审时需要做结构化 diff：

1. 先比较汇合前生成式出口量；
2. 再逐段比较 quota 截断、属性过滤、创意服务和粗排输入/输出；
3. 最后比较 cache 写入和 Ranking Fetch 返回。

这里的“新旧对比”只指 GprHub 内部实现。主 Retrieval Proxy 是正式流量中的并发基准，需要另外统计 main-only、side-only 和 overlap 候选。

## SID→TID→AID 漏斗

| 阶段             | 计数                | 下降的含义         |
| ---------------- | ------------------- | ------------------ |
| Decoder          | 去重 SID 数         | beam/模型输出      |
| KV pre-Z-order   | 所有分片 TID 总数   | SID 覆盖与 KV 命中 |
| KV post-Z-order  | 截断后 TID          | quota/交织影响     |
| Creative Build   | 成功映射 AID 的 TID | 正排/映射缺失      |
| AID dedupe       | 唯一广告数          | 多创意归并         |
| Common filtering | 过滤后广告/TID      | 库存与策略约束     |
| Scoring top-n    | 粗排输出            | 排序 quota         |
| Cache/Fetch      | 最终广告数          | 异步写读一致性     |

当空结果上升时，必须找到漏斗首次断崖的位置，而不是只看最终 `no_ad`。

## 多广告位与并发

- position 之间可以异步执行；
- 每个 position 必须拥有独立的参数、cache node 和监控 tag；
- 请求级共享 Encoder 只有在 schema/model 完全相同时才可复用；
- 合并 callback 必须处理部分成功，不应因为一个 position 失败而丢弃其他 position；
- cache key 必须含足够的请求/位置维度，避免 Ranking Fetch 读错。

召回之后的 Scoring、Ranking Fetch、双路精排与合并逻辑见 [[推荐系统理论/OneRec/召回粗排精排重排源码链路|召回、粗排、精排与重排源码链路]]。
