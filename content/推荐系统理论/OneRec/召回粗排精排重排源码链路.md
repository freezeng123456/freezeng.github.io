## 1. 先给出结论

当前线上拓扑可以概括为：

1. Mixer 构造一次召回请求，同时调度主路 Retrieval Proxy 和 GprHub 侧路；正式与灰度环境里，两路通常并发存在。
2. GprHub 侧路内部还有一次 A/B 选择：生成式开关打开时进入六节点 OneRec DAG；关闭时进入旧 GPR 对照实现。
3. 生成式 RPC 先向 Mixer 返回可供 Ranking 使用的侧路标识，真正的召回、过滤与粗排继续异步执行，结果写入按请求与广告位隔离的缓存。
4. Ranking 很早就启动侧路 Fetch。主路与侧路分别完成候选绑定、清洗、预测、pCTR 和出价上下文构建。
5. 两路在 `MergeMultiAds` 进行广告级与创意级合并，之后共享预测后处理、样式重排、模板重排、动态策略图、竞价和响应构建。
6. OneRec 的专用相关性分数只在满足开关、广告位和阈值条件时作为公共重排中的一个因子，不会替代整套重排器。

这套实现形成“并发侧路 + 晚合并 + 快速失败放行”的结构。OneRec 超时、缓存未命中或返回为空时，主路仍可继续产出结果。

## 2. 三种对比口径必须分开

当前资料最容易混淆的地方是“主路”“旧 GPR”“仿真隔离”三者。它们对应不同的代码分支。

| 对比口径                | 实验对象                       | 实际执行关系                            | 适合回答的问题                                  |
| ----------------------- | ------------------------------ | --------------------------------------- | ----------------------------------------------- |
| 线上主路 vs GprHub 侧路 | Retrieval Proxy 与 GprHub      | 正式/灰度环境通常并发，Ranking 后段合并 | OneRec 给最终候选和业务指标带来多少增量         |
| GprHub 内部新旧实现     | 六节点生成式 DAG 与旧 GPR 对照 | 同一广告位在侧路内部二选一              | 新生成式实现相对旧 GPR 的召回质量、时延与稳定性 |
| gprsim 隔离验证         | 仅保留指定侧路                 | 可跳过主召回，并可使用专用仿真路由      | 单链路回放、问题复现和 trace 对齐               |

因此，“同一广告位新旧路径互斥”只适用于 **GprHub 内部的新旧实现选择**。它不能用来描述正式流量中的“主路与侧路”，因为这两路会同时运行。

## 3. 一次请求的完整时序

### 3.1 Mixer：构造一次请求，派生两项任务

Mixer DAG 先执行 `BuildRetrievalRequest`，随后启动两项同级任务：

- 主路任务把请求发往 Retrieval Proxy；
- GprHub 任务按广告位检查全局开关、位置级实验和路由条件，再决定是否调用侧路。

GprHub 任务内部读取生成式开关：

- 开启：调用生成式入口；
- 关闭：调用旧 GPR 对照入口；
- 未命中侧路实验：不产生 GprHub action，主路照常执行。

`UpdateLocalCache` 等待主路任务以及 GprHub 入口调用完成，随后执行召回响应处理和 `RankingAction`。这里的“GprHub 完成”只表示入口已经返回侧路标识，生成式流水线可能仍在后台运行。

### 3.2 GprHub：先应答，再按广告位异步生产候选

生成式服务接到多广告位请求后执行以下步骤：

1. 把请求拆成单广告位子请求；
2. 每个子请求只保留对应的 `pos_id`、实验参数和必要上下文；
3. 在响应中写入 Ranking 后续 Fetch 所需的侧路标识；
4. 立即结束入口 RPC；
5. 为每个广告位启动独立异步任务，执行召回、公共过滤和粗排；
6. 完成后写入 Retrieval Cache，并唤醒可能正在等待的 Ranking Fetch。

入口 RPC 时延和候选生产时延因此是两个指标。只观察 Mixer → GprHub 的 RPC P99，会漏掉 Decoder、KV、粗排以及 Fetch 等待造成的尾延迟。

### 3.3 Ranking：主路继续，侧路 Fetch 并发等待

Ranking 在解析请求并合并上下文后，很早就启动侧路 Fetch；主路的广告表绑定、DocWash 和预测同时继续。若缓存已填充，Fetch 直接返回；若生产仍在进行，Fetch 在位置级超时预算内等待条件变量；若发生 key miss、timeout 或 empty result，侧路返回空集合，主路不受阻断。

## 4. 召回：主路和生成式侧路分别做什么

### 4.1 主路 Retrieval Proxy

主路执行多源召回，并在同一 DAG 中完成配额控制、库存/定向过滤、创意处理、分片和召回侧 Scoring。主路候选通过常规 Mixer 响应进入 Ranking。

正式与灰度环境里，GprHub 实验命中不会自动停掉主路。只有隔离仿真环境在满足专用条件时才跳过主路任务。评审线上数据时应先确认环境类型，避免把仿真 trace 当作生产拓扑。

### 4.2 GprHub 的生成式六节点

| 节点                       | 源码中的主要动作                                   | 核心产物                          | 首要失败表现                         |
| -------------------------- | -------------------------------------------------- | --------------------------------- | ------------------------------------ |
| Entry                      | 解析位置级实验、quota plan、trie/KV 版本与搜索参数 | 统一的 `GenerativeData` 上下文    | 参数未命中、版本缺失、非法宽度       |
| Datahub                    | 获取生成模型所需的行为序列和上下文                 | 模型输入序列                      | RPC 失败、源序列为空、过滤后为空     |
| Encoder                    | 构造编码请求，生成可复用用户表征                   | shared user embedding、模型上下文 | schema 或模型版本不一致              |
| Decoder / AnyRecall Search | 按层生成 token 路径并计算 SID 分数                 | SID 集合、SID→score               | beam 越界、输出为空、分数错位        |
| KV Creative                | 以 SID 查询分片 KV，汇总 TID 并做交织截断          | TID、SID/TID 映射、模型分数       | KV 版本错、分片 miss、quota 截断过重 |
| Creative List Build        | TID→AID，按 AID 去重并构造公共广告列表             | `MultiAdCreativeList`             | 正排缺失、全部被去重                 |

Decoder 将每层 token 按固定协议打包成 SID key，当前实现以固定层级位宽组合 64 位键；SID 的得分取完整路径的末层分数。模型、trie、KV 和打包协议必须绑定版本发布，任何一处层数或位宽漂移都会直接表现为 KV miss。

KV Creative 收到不同 SID 的 TID 列表后，先按分片代价排序，再按 SID 分组交织。截断发生在交织之后，使单个 SID 或单个分片难以占满全部配额。Creative List Build 随后完成 TID→AID 映射和 AID 去重，并把生成分数、统一策略与子策略带入公共广告对象。

### 4.3 GprHub 内部的新旧 DAG 对比

生成式 DAG 从现有 Retrieval Proxy 图复制了大部分公共结构，并用六个生成式节点替换旧的远程 GPR 节点。两张静态 DAG 的当前 diff 仍有少量差异：主图保留了额外的 AnyRecall/LTR、GNN 创意和提前 trace 类节点，生成图没有完全同步这些节点。

这项差异应作为架构评审事项保留：

- 若差异有意存在，需要写清业务原因及指标口径；
- 若属于图配置漂移，需要通过结构化 DAG diff 和单测阻止继续扩大；
- 做新旧实验归因时，比较边界应放在生成式出口、公共过滤出口和 Scoring 出口三个位置，不能只看最终广告数。

## 5. 粗排：召回侧 Scoring 的真实边界

生成式候选构造成公共广告列表后，继续经过：

```text
AdListMerge
  → 定向及库存过滤
  → 离线 / 在线 / 白名单过滤
  → OutputQuota 与多样性配额
  → CreativeFilter / PropertyFilter
  → CreativeServer
  → Sharding
  → Scoring subflow
  → ScoringExit
```

Scoring 子图内部按以下依赖执行：

1. 初始化粗排上下文；
2. 拉取或组装交叉特征；
3. 构建 Scoring 请求；
4. 调用粗排模型；
5. `ScoringExit` 把 top-n 和策略上下文写回召回响应。

这部分就是 OneRec 侧路的粗排。它发生在 GprHub 缓存写入之前，与 Ranking 内的精排预测属于两个独立阶段。评审指标需要同时覆盖：

- Scoring 输入/输出候选数；
- top-n 截断量；
- 交叉特征缺失率；
- 模型请求失败、超时和空响应；
- `ScoringExit` 到 cache 完成之间的序列化与写入耗时。

## 6. 异步缓存：生产者与消费者怎样握手

### 6.1 Cache node 的状态

每个广告位进入生成式 `DoRetrieval` 时创建独立 cache node。节点保存：

- 脱敏后的请求/广告位复合键；
- 处理开始与结束时间；
- 实验标签和召回路径；
- 粗排后的召回响应；
- `fill_done` 状态；
- fiber mutex 与 condition variable。

缓存采用分片 map 降低锁竞争，并有两类可配置清理条件：已填充节点的正常过期，以及生产过程失联时的硬过期。成功 Fetch 后会主动删除节点；后台清理负责兜住消费者缺席和异常退出。

### 6.2 生产者写入顺序

1. 创建节点并插入 cache；
2. 运行单广告位召回 DAG；
3. 在节点锁内写入响应、结束时间、实验标签和召回路径；
4. 最后设置 `fill_done=true`；
5. 释放锁并通知等待者。

`fill_done` 必须最后写。若先置位再补响应，Ranking 可能观察到完成状态却读到半成品。

### 6.3 Ranking Fetch 的读取顺序

1. 重新构造同一复合键；
2. cache miss 时立即返回空侧路；
3. 命中但未完成时，在位置级 timeout 内等待；
4. 被唤醒后再次检查完成条件；
5. 成功时复制响应并删除节点；
6. 分别上报 key miss、wait timeout、empty response、成功广告数和端到端时延。

### 6.4 需要单独观察的竞态窗口

| 窗口                       | 现象                                | 诊断依据                               |
| -------------------------- | ----------------------------------- | -------------------------------------- |
| Ranking 先到，生产者后到   | Fetch wait latency 上升，最终可成功 | cache hit、等待后 `fill_done`          |
| 生产者先完成，Ranking 后到 | Fetch 很快返回                      | cache age、接近零等待                  |
| Ranking 到达前节点已硬过期 | key miss                            | 生产耗时、缓存清理计数、Fetch 到达时间 |
| 生产者异常退出             | 等待直到 timeout 或硬过期           | 节点长期未完成、最后一个成功 Op        |
| 多广告位键冲突             | 返回错误位置的候选或实验标签        | position 维度校验、响应 tag 对账       |

## 7. 精排：Ranking 内的双支路

### 7.1 Fetch 与主路预处理并发

`FetchGprAction` 在 Ranking 合并基础上下文后启动，不需要等待主路完整 DocWash 结束。它按广告位并发请求 GprHub Fetch 接口，并把压缩的粗排响应还原成 Ranking 候选结构。

侧路候选绑定阶段会补齐广告表、出价信息、原始召回来源、创意模型及策略数据，同时标记 GPR/OneRec 来源和“侧路独有”状态。这样后续合并可以区分三类对象：主路独有、侧路独有、两路重合。

### 7.2 DocWash 并不对称

| 能力                        | 主路 DocWash   | GPR/OneRec DocWash                   |
| --------------------------- | -------------- | ------------------------------------ |
| 候选拆分与超时截断          | 完整           | 有基础拆分                           |
| 合约、RTA、同广告、素材过滤 | 完整多阶段     | 轻量路径，依赖召回侧已完成的部分过滤 |
| 洗牌/聚合页/特殊广告策略    | 按主路配置执行 | 未完整复刻                           |
| 创意展平与回并              | 完整           | 有专用 flatten/get/merge 链          |
| top-n 与 bucket 生成        | 主路完整实现   | 侧路保持自身候选集合                 |

这种不对称会影响实验解释。若两路过滤率不同，需先判断差异来自召回侧过滤、Ranking DocWash，还是字段绑定缺失。建议建立“主路字段—侧路字段”契约测试，并对每种删除原因做同口径计数。

### 7.3 两套预测与 pCTR

主路执行常规 `PredictionRequest → PctrAction`，侧路执行 GPR 专用 prediction request 和 pCTR action。两边还分别补齐 RTA、出价、生态、eGMV、pacing 和样式上下文，随后在公共 bid/ecosystem merge 附近对齐。

因此，OneRec 的“精排增量”应拆成三部分：

1. 新增候选带来的覆盖增量；
2. 侧路独立预测分数带来的排序增量；
3. 与主路重合候选在合并后保留更多模型/策略信息带来的增量。

## 8. 合并与重排：晚合并的具体语义

![OneRec 在 Ranking 中的候选绑定、合并与公共重排](assets/diagrams/onerec/zh/ranking-merge-detail.svg)

### 8.1 `MergeMultiAds` 的广告级合并

合并算子先以主路候选建立 AID 索引，再逐个处理侧路候选：

- AID 未出现：把侧路广告追加为新候选；
- AID 已出现：保留一个广告对象，同时合并主路/GPR 召回来源、策略和配额信息；
- 重合广告清除“仅侧路”标记，并同时保留 normal 与 GPR 归因标签。

广告数因此不等于两路候选数之和。需要同时上报 `main_count`、`gpr_count`、`overlap_aid_count` 和 `merged_unique_aid_count`。

### 8.2 创意级合并与全局去重

同一广告内，代码以创意尺寸和创意 ID 识别同一创意：

- 同创意合并 GPR 模型、策略和分数；
- 侧路独有创意追加到广告的创意列表；
- 完成广告级合并后，再按全局创意唯一标识去重；
- 冲突时先比较出价校正后的价值，仍相同时选择更新的创意。

这一步可能改变最终创意归属，因此必须监控侧路候选是否缺少出价、生态或重排因子。缺字段会让去重 winner 产生系统性偏差。

### 8.3 公共重排

合并后依次执行：

```text
MergeMultiPredictionRecommendContext
  → PredictionPostProcess
  → UpdateAdxRecommendContext
  → RerankingPreProcess
  → StyleReranking
  → TemplateReranking
  → Dynamic Reranking Graph
  → RerankingPostProcess
  → AdLoad / strategy execution
  → Response
```

OneRec 相关性优化在特定广告位、全局开关和位置级实验同时命中时读取生成式体验分数，经阈值判断与 $[0,1]$ 截断后作为相关性因子。它属于公共重排图中的可选输入；评价收益时需要单独分桶，防止把“生成式召回收益”和“重排因子收益”合在同一指标里。

## 9. 关键参数及其源码作用点

| 层级          | 参数                                           | 解析位置与生效规则                                          | 首先影响                       |
| ------------- | ---------------------------------------------- | ----------------------------------------------------------- | ------------------------------ |
| Mixer 路由    | GprHub enable / call gate                      | 全局能力、位置实验和路由条件同时满足才创建侧路 action       | 侧路 QPS                       |
| 侧路内部 A/B  | `mixer_enable_generative_recall`               | 选择生成式 RPC 或旧 GPR 对照 RPC                            | 召回实现与 `recall_path`       |
| 生成搜索      | `gpr_pam_beam_width`                           | Entry 解析；缺失时有效回退 180，当前 Decoder 支持上限为 180 | Decoder 计算量、SID 数、P99    |
| 最终 SID 截断 | `gpr_beam_search_topk`                         | 大于 0 时生效；缺失不应臆造生产值                           | Decoder 出口 SID 数            |
| Beam 分片     | `gpr_pam_beam_width_shard_ratio`               | 按位置实验读取，需与总 beam 预算一致                        | 分片负载与候选分布             |

| Fetch 等待    | `gpr_server_hub_timeout_ms` / service fallback | 位置级值优先；必须落在主链路总预算内                        | timeout、侧路覆盖、Ranking P99 |

## 10. 主路与 OneRec 侧路逐阶段对照

| 阶段         | 主路                 | OneRec / GprHub 侧路                  | 公平对比所需口径                       |
| ------------ | -------------------- | ------------------------------------- | -------------------------------------- |
| 触发         | 默认主召回任务       | 全局 + 位置实验 + 路由命中            | 同请求、同 position、同时间窗          |
| 召回         | 多源 Retrieval Proxy | 六节点生成式 DAG 或旧 GPR 对照        | 分开报告“主路 vs 侧路”和“侧路新 vs 旧” |
| 过滤与 quota | 主召回 DAG           | GprHub 克隆的公共 DAG，存在少量图差异 | 对比每节点 input/output 与删除原因     |
| 粗排         | 主路 Scoring 子图    | 侧路 Scoring 子图                     | 特征完整率、top-n、模型版本、P99       |
| 交接 Ranking | 常规召回响应         | 异步 cache + Fetch                    | request-to-cache、wait、miss、timeout  |
| 候选绑定     | 主广告表链           | Fetch 后专用绑定链                    | AID/TID/creative 字段覆盖率            |
| DocWash      | 完整主路流程         | 轻量专用流程                          | 删除原因与前置过滤责任边界             |
| 精排         | 主 prediction / pCTR | 侧路 prediction / pCTR                | 分数校准、特征缺失、推理时延           |
| 合并         | 提供基准候选         | AID 重合合并，独有候选追加            | overlap AID/creative、字段冲突         |
| 重排         | 与侧路共享           | 与主路共享；可选 OneRec 因子          | 因子开关分桶、公共策略版本             |
| 失败         | 影响主体响应         | miss/timeout/empty 快速放行           | 主路成功率保持稳定                     |

## 11. 端到端漏斗与延迟账本

### 11.1 候选漏斗

```text
请求命中 GprHub
  → Datahub 有效序列
  → Decoder unique SID
  → KV pre-interleave TID
  → KV post-quota TID
  → TID→AID 成功
  → AID dedupe
  → 公共过滤后候选
  → Scoring top-n
  → cache fill
  → Ranking Fetch return
  → GPR DocWash output
  → GPR fine-rank output
  → Merge side-only / overlap
  → common rerank winner
  → final exposure
```

每个箭头都应同时记录绝对量、转化率、失败原因和位置级分桶。只看最终曝光会把模型、库存、缓存和 Ranking 问题混在一起。

### 11.2 延迟账本

端到端等待关系可以写成：

$$
T_{\text{side-ready}} = T_{\text{datahub}} + T_{\text{encoder}} + T_{\text{decoder}} + T_{\text{kv}} + T_{\text{filter}} + T_{\text{coarse}} + T_{\text{cache-write}}.
$$

Ranking Fetch 的实际等待量近似为：

$$
T_{\text{wait}} = \max\left(0,\;T_{\text{side-ready}}-T_{\text{ranking-arrival}}\right),
$$

并受到位置级 Fetch timeout 截断。主路 Ranking 与 GprHub 异步生产存在重叠，不能把各阶段 P99 直接相加当成用户侧总时延。正确做法是同时画 request timeline、critical path 和 wait-time 分布。

## 12. 源码核验索引

下面保留可复核的逻辑锚点，不暴露内部路径。

| 逻辑锚点                 | 核验到的行为                                      | 文档中的结论                               |
| ------------------------ | ------------------------------------------------- | ------------------------------------------ |
| Mixer DAG                | 主召回任务与 GprHub 任务依赖同一请求构建节点      | 正式流量两路并发                           |
| GprHub task              | 生成式开关只决定侧路 RPC 类型                     | “新旧互斥”属于侧路内部                     |
| Retrieval Proxy guard    | 仅隔离仿真模式在特定条件下跳过主任务              | 仿真拓扑不可外推到生产                     |
| Generative service entry | 多广告位拆分、入口先返回、后台 fiber 继续         | 入口 RPC 与候选完成时延分离                |
| Retrieval cache          | 分片 map、完成条件、等待通知、成功删除、软/硬清理 | Fetch 是同步消费者，生产端异步             |
| Generative DAG           | 六节点替换旧 GPR 节点，之后进入公共过滤与 Scoring | OneRec 侧路含完整召回与粗排                |
| Ranking Fetch            | 早于主 DocWash 完成启动，按广告位并发             | Fetch 等待与主路预处理重叠                 |
| GPR Ranking branch       | 专用绑定、轻量 DocWash、独立 prediction/pCTR      | 侧路有独立精排，且清洗能力与主路不完全相同 |
| Multi-path merge         | AID 合并、创意合并、全局创意去重                  | 两路候选量不能直接相加                     |
| Common reranking         | 样式、模板、动态策略共享；OneRec 因子条件启用     | 召回收益与重排因子收益需分桶               |

## 13. 本轮评审应优先关闭的问题

1. **DAG 漂移**：为主图与生成图建立机器可读的节点/依赖 diff，明确允许差异。
2. **DocWash 不对称**：补全字段契约和删除原因对账，确认轻量路径没有漏掉必须的安全/业务过滤。
3. **超时预算**：用当前分位置 P95/P99 重算 Fetch timeout，满足侧路覆盖率的同时守住主路总预算。
4. **最终参数可见性**：每个请求上报最终 beam、top-k、quota、trie/KV 版本、Fetch timeout 和模型版本。
5. **多广告位隔离**：对参数、cache key、tag、timeout 和 partial success 增加端到端测试。
6. **合并字段完整性**：监控重合广告的 bid、生态、模型分数、策略 quota 和 rerank factor 缺失率。
7. **收益拆解**：同时保留 main-only、side-only、overlap、OneRec rerank-factor on/off 四个维度。
8. **环境标识**：在 trace 顶层标注 production/gray/gprsim，避免把隔离仿真结论写入线上复盘。

稳定性指标和告警结构见 [[推荐系统理论/OneRec/稳定性与可观测性|稳定性与可观测性]]。
