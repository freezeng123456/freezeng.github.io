## 稳定性目标

| 目标   | 要求                                               |
| ------ | -------------------------------------------------- |
| 可回滚 | 请求级关闭 GprHub 侧路或切换其内部实现，不依赖发版 |
| 可对照 | 主路/侧路与侧路内部新旧实现分别使用一致口径        |
| 可定位 | 空结果/慢请求可定位到 Op、RPC 或漏斗阶段           |
| 可降级 | OneRec 失败不阻塞主链路                            |
| 可审计 | 最终生效参数与模型/KV 版本可追溯                   |

## 三层开关

1. **侧路启用开关**：决定是否在主 Retrieval Proxy 之外创建 GprHub action。
2. **侧路实现开关**：在 GprHub action 内选择生成式 RPC 或旧 GPR 对照 RPC。
3. **GprHub 服务能力开关**：决定是否创建或启用生成式 flow runner。

回滚顺序：

- 整条侧路指标异常：关闭 GprHub action，保留并验证主路结果；
- 仅生成式实现异常：把侧路切到旧 GPR 对照 RPC；
- 新 DAG 代码异常：关闭 set 级开关并重启对应 set；
- Fetch 超时：停止扩量，核对 pipeline P99 与 Ranking 预算；
- 模型/KV 版本错误：回滚模型包和 KV 版本，不能只调 beam。

## 灰度节奏

```text
部署（开关默认关）
  → 1%
  → 5%
  → 50%
  → 100%
  → 侧路内部旧 GPR 对照 QPS 归零
  → 评估清理侧路 legacy 实现
```

这条灰度序列针对 GprHub 内部的生成式替换。主 Retrieval Proxy 是否退休属于另一项架构决策，不能随着侧路全量自动执行。

每一步至少比较：

- 请求/成功/失败 QPS；
- GprHub 与 Fetch P95/P99；
- cache 写入和 Fetch 返回广告数；
- SID→TID→AID 漏斗；
- quota/过滤/粗排删量；
- 业务护栏。

## 三块看板

### 1. Mixer → GprHub

核心指标：

- recall request/success/fail；
- GprHub recall latency P99；
- cache ad count；
- request-to-cache latency；
- no-ad count。

它回答：GprHub action 是否命中、侧路是否按时写 cache。主 Retrieval Proxy 需要保留并行成功率和候选量作为基准。

### 2. 生成式流水线

每个 Op 上报：

- entry count；
- latency/P99；
- failed count；
- empty output；
- input/output ad count。

Datahub、Encoder、Decoder、KV 分别上报 RPC request/fail/latency。再加 SID→TID 漏斗：

```text
sid_key
  → kv_tid_pre_zorder
  → decoder_tids
  → creative_build_tid
  → unique_aid
```

它回答：新路径内部在哪一段丢量或变慢。

### 3. Ranking Fetch

核心指标：

- Fetch QPS、fail、timeout、key miss；
- Fetch latency 与 wait latency；
- response ad count / no-ad；
- cache 写完成到 Fetch 成功的端到端延迟。

它回答：Ranking 是否及时拿到侧路结果。

## 两层对比看板

第一层比较 GprHub 内部生成式实现与旧 GPR 对照。在召回 DAG 的 `AdListMerge` 之后，用 `recall_path` + `exp_tag` 对比：

| 阶段               | 重点                                       |
| ------------------ | ------------------------------------------ |
| OutputQuotaControl | 截断广告数、触发次数                       |
| PropertyFilter     | TID input/output 与删量率                  |
| CreativeServer     | 空 shard、请求/响应广告数、准备耗时        |
| Scoring            | 输入 TID/AID、top-n、响应大小              |
| Flow node          | 每个 Op latency、input/output、失败/空结果 |

第二层比较正式流量中的主路和 GprHub 侧路。Ranking 合并处需要增加：

- main-only、side-only 与 AID overlap；
- creative overlap、侧路新增创意和全局 creative dedupe；
- 主/GPR DocWash 删除原因；
- 主/GPR prediction、pCTR 和出价上下文字段完整率；
- OneRec 重排因子 on/off 分桶。

归因顺序必须从上游到下游。若生成式出口已经不同，最终广告差异不能直接归给粗排；若召回侧一致而 GPR DocWash 后下降，才检查 Ranking 字段和过滤契约。

## 评审阈值

阈值必须根据当前线上基线和位置级预算计算，旧联调快照中的绝对数字不应继续沿用：

| 护栏                   | 暂停扩量条件                                 |
| ---------------------- | -------------------------------------------- |
| GprHub cache-ready P99 | 突破该 position 的侧路预算并持续跨过告警窗口 |
| 分段 RPC 失败率        | 显著高于同机型、同位置、同实验基线           |
| Fetch timeout          | 侧路覆盖下降，且等待已经挤占主路总预算       |
| 空结果                 | 相对 GprHub 旧实现或同实验基线显著升高       |
| 主路健康度             | 主路成功率、P99 或最终响应量出现回归         |

阈值需要用流量、机型和 position 分桶。全局平均会掩盖长尾广告位。

## 清理侧路 legacy 实现的门槛

GprHub 内部旧 GPR 对照实现只有在以下条件同时成立后才能下线：

1. 新路径全量且稳定跨过观察窗口；
2. 侧路回滚不再依赖旧实现，或已有等价灾备；
3. 旧 GPR 对照 QPS 持续为零；
4. 新旧看板、报警和 on-call 手册完备；
5. 旧 Datahub workflow、侧路 `RemoteGprOp`、服务路由和图配置有明确删除清单；
6. 删除前完成一次反向切流演练。

主 Retrieval Proxy 的退场需要单独证明主路能力已被完整替代，包括多源召回、完整 DocWash、字段契约和灾备；本页不把它纳入侧路 legacy 清理范围。
