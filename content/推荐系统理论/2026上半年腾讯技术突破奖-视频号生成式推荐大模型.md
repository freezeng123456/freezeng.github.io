## 先看结论

短视频分发要同时应对两条一起变大的曲线：用户兴趣的复杂度，以及内容池的规模。传统推荐用「召回—粗排—精排—重排」的漏斗来承接这种规模，每一级用判别式模型对候选独立打分，再把幸存者交给下一级。这个结构便于工程实现，但它在三个位置持续损失信息：

1. 召回为了能建索引，必须把用户与视频的交互压缩成一次顶层内积；
2. 粗精排为了控制成本，把长历史剪枝成短序列，再用人工设计的结构完成特征交叉；
3. 重排把最终排列交给几十条互不通气的生成通道和一层规则。

三处损失有同一个来源：链路把「检索、打分、拼装」拆成彼此独立的子问题，每个子问题都有自己的目标函数和候选空间。生成式推荐给出的答案是把它们改写成同一件事——在统一的价值口径下直接生成结果。把推荐重述为生成任务的代表性公开工作包括 [HSTU](https://arxiv.org/abs/2402.17152) 与 [OneRec](https://arxiv.org/abs/2502.18965)。

![三段链路被同一种生成式改写替换](assets/diagrams/generative-recommendation/zh/stack-shift.svg)

三条改写路径彼此独立，可以分别落地：

- **召回**从「编码用户、检索邻居」变成「直接生成视频的语义 ID」，索引不再是模型能力的天花板；
- **粗精排**沿两条 Scaling 轴前进——序列长度与 Dense 参数量，前者需要为多特征域重新设计注意力，后者需要先解决梯度坍缩；
- **重排**从「多通道加规则漏斗」变成「一个自回归模型生成整条序列」，并让强化学习去优化这条序列的整体价值。

## 1. 判别式链路在哪里丢信息

### 1.1 召回：索引形态倒逼模型形态

向量化召回要在极大的内容池上做近邻检索，因此模型必须先把用户和视频各自编码成一个向量，再用内积衡量匹配度。这个约束由索引带来，不是建模需要：交叉只能发生在最顶层，底层特征之间的复杂交互没有表达空间。

由此派生出三个次生问题。第一，近邻检索本身是近似的，索引效率与检索精度之间存在折损。第二，同一套索引在相近请求下会给出高度重合的结果，多样性差。第三，召回的训练目标（通常是采样负例下的匹配任务）与后链路的排序目标不同源，链路一致性差——召回认为好的候选，排序未必认可。

### 1.2 粗精排：两阶段序列与手工交叉

长序列建模的常见做法是两阶段：先用一个廉价的检索单元从上万条历史里挑出几十到几百条，再让精细模型在这个子集上做目标感知的注意力。这条路线工程成熟度很高，各种变体的取舍见[[推荐系统理论/长序列建模\|长序列建模的技术路线]]，但剪枝这一步不可逆：被丢掉的行为里可能恰好包含兴趣迁移的过渡轨迹。

即便对保留下来的部分，建模方式也偏窄。目标感知注意力本质上在回答「目标视频和每条历史视频有多像」，刻画的是相似度匹配，而不是序列自身的兴趣演进轨迹。

Dense 侧是另一类问题。CTR 模型里的特征交叉长期依赖人工设计的结构，这些结构的参数容量有限，把它们简单放大并不会换来相应的收益。

### 1.3 重排：规则漏斗与小候选

重排负责把精排给出的候选拼成用户真正看到的那一屏。行业常见形态是几十条生成通道并行产出候选序列，再用一层规则和公式挑选。这个形态有四个连带后果：通道之间彼此不感知，各自优化；系统行为主要由规则决定，而不是由模型决定；候选规模只有数十量级，远小于精排的输出；评估环节退化成一个标量打分，无法表达「这一屏整体好不好」。

因此重排的上限不取决于某条通道调得好不好，而取决于形态本身。

## 2. 生成式重排：把漏斗改写成一次生成

重排可以拆成两个子问题：怎样生成高质量的序列，以及怎样判断用户会不会满意。前者是生成模块，后者是评估模块。把生成模块统一成一个自回归模型，是整条改写路径的支点。相关思路的公开介绍见[微信视频号的生成式重排技术文章](https://mp.weixin.qq.com/s/zhkVh8UauwdKmbLThD9v8A)。

统一之后，一个模型需要同时满足三项此前由不同通道分别承担的要求：

| 要求     | 含义                                 | 对应设计                     |
| -------- | ------------------------------------ | ---------------------------- |
| 生成质量 | 生成的序列在整体价值上要优于规则拼装 | 以评估打分为奖励的强化学习   |
| 可调参性 | 线上策略变更频繁，模型必须跟得上     | 把规则与公式指令化后写进输入 |
| 检索效率 | 生成更多候选序列时，收益不能立刻饱和 | 序列集合级的端到端生成       |

![统一生成模型与两端 Scaling](assets/diagrams/generative-recommendation/zh/rerank-unification.svg)

### 2.1 用强化学习优化整条序列

监督学习只能拟合「历史上出现过的排列」，无法直接优化「这条排列值多少」。强化学习提供了这条通路：推理阶段评估模块给每条候选序列的打分被落盘保存，训练阶段把它当作奖励，用 policy gradient 更新生成模型。训练与推理因此共用同一套打分，构成闭环。

这个朴素形式有两个可预期的问题。其一，不同请求下评估模块的绝对分数不可比；其二，分数会突变，个别极端样本足以主导梯度。把原始奖励换成组内排名归一化后的值可以同时缓解这两点——排序信息保留了，尺度被压平了。

在此之上可以引入偏好式目标。[DPO](https://arxiv.org/abs/2305.18290) 不需要显式的奖励模型，直接在「更好的序列」与「更差的序列」之间做对比训练。序列级的对比仍然偏粗：一条序列可能只在某个位置排错，整条被判负会把正确的前缀一并惩罚。把偏好信号收敛到第一个出错的位置就得到逐步偏好优化，长链推理上的对应工作是 [Step-DPO](https://arxiv.org/abs/2406.18629)。

再往后是从大模型强化学习迁移过来的一组稳定性技巧：

- **组内优势**：一次采样多条序列，用组内均值与标准差把奖励标准化成优势，省去单独的价值网络，思路见 [GRPO](https://arxiv.org/abs/2402.03300)；
- **梯度截断**：对更新幅度设上界，让离群样本不至于破坏训练稳定性，同时避免直接丢弃这些样本；
- **序列级重要性采样**：采样用的是线上模型、更新的是训练模型，两者存在分布差异；在序列似然层面而非 token 层面构造重要性比值可以纠正这种偏移，思路见 [GSPO](https://arxiv.org/abs/2507.18071)。

经过多版迭代，模型化通道从少数派变成主力通道。这里重要的不是占比本身，而是它的含义：只有当绝大部分曝光都由同一个模型产生时，后续的 Scaling 才有统一的作用面。

### 2.2 指令跟随：把线上策略变成模型输入

重排是整条链路里策略最密集的环节，变更频繁到无法为每次调整重新训练模型。可行的做法是让模型感知策略，而不是记住策略。

线上策略大致分两类。**规则**类的共同结构是「某类视频在某个窗口内出现的数量约束」，可以压成一个四元组：命中规则的视频、窗口的起点、窗口的长度、这个窗口内出现次数的下限与上限。打散、强插、保量这些看起来不同的规则，写成四元组之后是同一种东西。把它作为视频侧特征喂给模型，模型就能在生成时感知约束。为了让模型对新增规则也具备泛化能力，训练时可以对规则标签做随机化，迫使模型学到的是「如何满足一个四元组」，而不是「如何满足第某号规则」。

**公式**类策略是带超参的打分表达式。做法类似：把公式项连同超参一起输入，模型学到的是「在给定公式下生成序列」，超参改动时不需要重训。

这一步把建模目标从「生成一条序列」改写成「生成一条满足给定条件的序列」，实质上是给推荐模型加了一个 prompt 接口。

### 2.3 序列集合建模：把生成单位提到集合层面

统一之后自然的下一步是 test-time scaling：多生成几条候选序列，让评估模块挑最好的。但直接扩大生成条数很快就会饱和。

原因在 Beam Search 的贪心性质。同一个模型在同一个请求上生成的多条序列高度趋同——它们共享前缀，只在末端有差别，覆盖的其实是解空间里的同一个局部。多通道时代之所以还能靠「通道多」取胜，恰恰是因为不同通道的先验偏置不同，彼此差异显著。

要突破这一点，需要让候选序列在生成过程中互相知道对方的存在。具体做法是把生成单位从序列升级到序列集合：每一步生成时，先把每条在建的序列各自归约成一个向量，用一个 Transformer 让这些向量彼此感知，再决定各自的下一步。奖励也随之改写——不再奖励单条胜出的序列，而是奖励在多通道竞争中整体胜出的集合。

集合的动作空间比序列大得多，但正因为集合内的元素被要求互补而不是各自最优，同样的生成预算下检索效率明显高于「单序列建模加 Beam Search」这一经典组合。

### 2.4 统一之后，两端才有 Scaling 空间

统一生成本身不是目的。它的价值在于把重排从一个规则系统变成一个模型系统，从而让前后两个方向的 Scaling 有地方落。

**向前是候选规模。** 精排与重排之间原本存在一个漏斗：精排输出数百个候选，重排只处理其中几十个。统一生成让重排的算力预算可以集中投放，候选规模因此可以一路扩到覆盖精排全量输出，精重排之间的漏斗被直接消除。

**向后是评估系统。** 生成能力变强之后，评估可以从单一标量扩展成结构化的奖励体系：多个时间窗口（即时、会话、长期）×多种聚合算子（求和、取最大、取最小）×多种行为（时长、互动、退出）。这个乘积空间给出 List 级信号；在此之上再叠加 Point 级信号。有效信号的数量决定评估系统能分辨多细的差别，也就决定生成模型能被推到多高。

两个方向都依赖同一个前提：生成侧是一个模型，而不是几十条通道。

## 3. 生成式召回：从「检索一个向量」到「生成一个 ID」

召回决定整条链路的候选上界。生成式召回要解决的三件事——对齐后链路的价值口径、提升模型的交叉能力、去掉检索折损——都指向同一个动作：不再检索，直接生成。

### 3.1 自回归语义 ID 生成

[TIGER](https://arxiv.org/abs/2305.05065) 的思路是给每个 item 分配一组分层的离散 token（语义 ID），用 RQ-VAE 对 item 表征做多级残差量化得到，再训练一个 seq2seq 模型自回归地预测下一个 item 的语义 ID。检索因此被改写成解码：模型不再在向量空间里找邻居，而是逐级把 ID 写出来。[OneRec](https://arxiv.org/abs/2502.18965) 把这条路线推到工业规模，用统一的生成模型取代级联的召回—排序框架。

工业落地时有一个关键改动。TIGER 一类工作用内容侧的多模态表征做 tokenize，这在推荐任务里并不完备：多模态表征描述「视频是什么」，不描述「什么样的用户会看它」，缺少协同信息。改用视频 ID 表征可以补上这一维，代价是 ID 表征本身是动态的——新视频不断进入，老视频的表征持续更新——因此 tokenizer 也必须是流式的，随表征漂移滚动更新码本。相比冻结的多模态 tokenizer，流式 ID tokenizer 在实时性、稳定性、码本占用的均衡度以及与后链路语义空间的对齐上都更合适。

模型结构是标准的 Encoder-Decoder：Encoder 编码用户行为序列，Decoder 自回归地逐级生成语义 ID 的各层 token，再用 Beam Search 展开出一批结果作为候选集。相对判别式召回，它带来三处结构性优势：

- **一致性**：生成式训练可以在码本空间上做全负例，不必依赖采样负例去近似 softmax，训练目标与线上打分口径同源；
- **多样性**：Beam Search 天然产出一组彼此不同的路径，不像近邻检索那样把结果压在同一片邻域；
- **模型上限**：多层 Decoder、Sparse MoE 等结构可以直接堆上去，容量不再被索引形态限制。

推理成本是这条路线的主要代价：自回归意味着逐级解码，延迟随层级线性增长。多 token 预测（MTP）在一次前向里预测多个后续 token，是缓解这一点的常用手段。该链路的实现级细节见[[推荐系统理论/OneRec/index\|OneRec 工业实现链路]]。

### 3.2 扩散召回

自回归不是唯一的生成范式。扩散模型给出另一条路：先定义一个把真实分布逐步加噪、直至变成纯噪声的前向过程，再训练一个模型把噪声逐步还原回真实分布，还原时可以注入 condition 来引导方向。

用在召回上，各部件的对应关系是：

- **起点**是高斯噪声；
- **终点**是用户真正感兴趣的目标视频的表征；
- **condition** 是用户兴趣，由历史行为聚类得到；
- **训练目标**是在加噪路径的插值点上预测速度场，即 flow matching 一类的连续时间形式（见 [Flow Matching](https://arxiv.org/abs/2210.02747)）。

推理时从噪声出发，沿速度场积分若干步，得到一个落在 item 表征空间里的点。相比自回归，它的迭代次数与 item 的编码长度无关，而且用户兴趣以 condition 的形式显式出现，天然支持「给定兴趣、生成对应内容」这类控制方式。代价是它输出的是连续表征而非离散 ID，仍然需要一步从表征映射回具体视频。

## 4. 粗精排：沿两条轴 Scaling

大语言模型近年主要沿两个方向放大：上下文长度与 Dense 参数量。推荐任务有对应的两条轴——用户行为序列的长度，以及特征交叉部分的稠密参数量。两条轴各有各的障碍。

### 4.1 长序列：为多特征域重新设计注意力

第一步是把两阶段序列建模换成端到端建模，让模型直接看到完整历史，长度推到万级。但直接把标准 Transformer 搬过来，收益往往不显著。原因要回到推荐与文本的差别。

文本是**单特征域序列**：每个位置就是一个 token，注意力刻画的是 token 与 token 的关联，信号是二维的（序列 × 表示）。推荐是**多特征域序列**：每个位置是一次行为，而一次行为同时携带内容域（视频、作者、类目）、行为域（完播、点赞、转发）与上下文域（位置、时刻、场景）等多组特征。信号因此是三维的（序列 × 特征域 × 表示），而域与域之间的交叉正是推荐任务中高阶稀疏 pattern 的来源。标准 Transformer 把一个位置的所有域拼成一个向量后再算注意力，这一维在进入注意力之前就被压平了。

Cross-mask Transformer 让这一维显式参与计算，可以分成三步：

![Cross-mask 注意力如何处理多特征域的序列信号](assets/diagrams/generative-recommendation/zh/cross-mask-field-signal.svg)

1. **分域计算注意力分数。** 每个特征域单独算一份 attention score，得到若干视角下的 i2i 关联；「内容上像」和「行为模式上像」是两件不同的事，分开算才不会互相稀释。
2. **分数乘以域掩码。** 把某一域的 attention score 与另一域的 mask 逐元素相乘，域与域之间的交叉因此成为注意力矩阵里的显式结构，而不是隐含在拼接向量中。
3. **跨域聚合取值。** 用交叉后的分数去聚合各个域的 value，得到特征域的二阶交叉表示。

形式上可以概括为 $\sigma(QK^{\top}) \odot M$：注意力分数按域拆开计算，再按掩码组合。相对经典 Transformer，这种结构在推荐任务上表现出更好的 Scaling 性质——加长序列、加大容量时收益衰减得更慢。

成本方面，计算共享、零训练外推、零显存计算等一组优化把自注意力开销压低了一半以上；配合样本聚合，万级长度的 Transformer 结构才具备上线条件。这类由结构先验定义稀疏交互的路线与检索、压缩、层次化之间的取舍关系见[[推荐系统理论/长序列建模\|长序列建模]]，同一思路的公开介绍见[微信视频号的长序列建模技术文章](https://mp.weixin.qq.com/s/xPidLQfNEF-fCCVksT9u_w)。

### 4.2 Dense：先解决梯度坍缩，再谈 Scaling

第二条轴是稠密参数。[RankMixer](https://arxiv.org/abs/2507.15551) 给出一个适合 GPU 的结构：把特征按语义分组，每组压成一个 token，每个 token 过一个专属的 per-token FFN；稠密参数量由这些 FFN 的隐层宽度决定，加宽即可放大。token 之间的交叉不用二次注意力，而用 mixing——先把每个 token 切成若干段，再跨 token 把序号相同的段重新组合成新 token，交叉因此只需要一次重排。

问题出在放大之后。稠密参数一多，模型反而容易坍缩，而这种坍缩在原始坐标系下是隐蔽的：梯度矩阵在每一个坐标方向上都有非零投影，看起来一切正常。把梯度做特征值分解、换到本征坐标系再看，真相才显现——能量几乎全部集中在少数几个主成分方向上，其余方向的奇异值接近零。参数变多了，有效更新方向并没有变多。

解法是正交化：对梯度做正交化处理，把各向异性的更新拉回各向同性，让每个方向获得可比的更新幅度。这正是 [Muon](https://arxiv.org/abs/2502.16982) 一类基于矩阵正交化的优化器在大模型训练中所做的事。放到 Dense Scaling 场景，它把「参数增加但收益停滞」的曲线重新拉起来，使这条轴恢复可 Scaling。

> [!important] 坍缩要在本征空间里看
> 判断 Dense 参数是否被有效利用，不能只看梯度在原始坐标下是否非零。可观测的量是梯度矩阵的奇异值谱：谱越平，更新越接近各向同性；能量集中在前几个奇异值上，就说明有效秩远低于参数量，继续加宽不会带来收益。

## 5. 三段放在一起看

| 环节   | 判别式形态的核心约束                 | 生成式改写                                 | 新增的工程成本                                 |
| ------ | ------------------------------------ | ------------------------------------------ | ---------------------------------------------- |
| 召回   | 索引要求顶层内积，交叉能力被封死     | 自回归生成语义 ID；扩散生成 item 表征      | tokenizer 与码本的流式更新、逐级解码的推理开销 |
| 粗精排 | 序列剪枝丢信息，Dense 交叉靠手工结构 | Cross-mask 建模多域 3D 信号；正交化解坍缩  | 稀疏注意力 kernel、长序列样本组织、优化器开销  |
| 重排   | 通道各自为战，规则拼装，候选极小     | 统一自回归生成、强化学习目标、复杂奖励体系 | 奖励落盘链路、指令体系维护、集合生成的解码成本 |

三行的共同点是：模型承担了原本由索引、剪枝规则和拼装规则承担的职责。这不是免费的交换。生成式方案把成本从「维护一堆启发式」搬到「训练算力、奖励系统设计和推理效率优化」上，只有当后者的边际收益确实高于前者，改写才成立。成立的条件通常需要三点同时满足：候选空间足够大，行为信号足够密，算力预算允许把这些信号真正用起来。

## 6. 落地时的评审要点

### 目标一致性

- 召回、排序、重排是否共用同一套价值口径？若不共用，差异出现在哪一层，能否量化？
- 奖励体系里的每一路信号是否都能追溯到一个业务含义，还是有些信号只是「加上去指标会涨」？
- 生成模型的训练目标与评估模块的打分口径是否会随版本漂移？

### 训练与推理的一致性

- 推理阶段落盘的打分与训练阶段使用的奖励是否来自同一版本的评估模型？
- 指令（规则四元组、公式项）在训练样本与线上请求中的分布是否一致？新增规则怎样进入训练集？
- 采样策略（Beam 宽度、集合生成的集合大小）在离线评估与线上是否一致？

### 可控性

- 策略变更是否真的不需要重训？变更后多久能在生成结果里观察到响应？
- 模型不遵守某条硬约束时，兜底路径是什么？规则通道是否保留为回退？
- 规则标签随机化之后，模型对没见过的规则编号是否仍然满足约束？

### 成本与稳定性

- 自回归解码、集合生成、长序列注意力各自的延迟占比是多少？稀疏结构在 kernel 层面是否真的跳过了无效计算？
- 语义 ID 码本滚动更新时，历史样本里的旧 token 如何处理？码本版本与线上模型版本如何对齐？
- 强化学习的奖励分布漂移（评估模型换版、口径调整）如何监控与回滚？
